# 문서 관리 절차: ADR 두 벌, Timeline, 머지 후 갱신

## 배경

#10까지 진행하고 보니 문서를 읽을 순서를 찾기 어려웠다. 확인한 원인은 네 가지다.

- Obsidian `Overview`의 문서 지도가 11-05에서 멈춰 있었다.
- #17에서 ADR을 저장소로 옮긴 뒤에도 Obsidian에 옛 사본 6개가 남았다. 그중 4개는 저장소와 내용이 달랐다.
- Devlog는 쓴 날짜로만 나뉘고 PR 링크가 없었다. #2, #4 기록도 빠져 있었다.
- Devlog의 리뷰 수치가 2차 리뷰 전 값으로 남았다.

범위 밖: Obsidian 노트 자체는 저장소에 넣지 않는다.

## 결정과 이유

| 결정 | 이유 |
|---|---|
| ADR을 두 벌로 쓴다. 저장소 `docs/adr`은 핵심만 빠르게 이해시키는 요약판이고, Obsidian `ADR/<area>/`은 상세판이다. 상세판에는 배경, 검토한 방안과 장단점, 선택 이유, 기각 이유, 핵심 코드를 넣는다 | 사용자 결정이다. 저장소 독자(리뷰어, 다음 세션)는 결론과 주의점이 필요하다. 사용자는 Rust 학습과 회고를 위해 방안 비교와 실제 코드까지 읽는다 |
| 원본은 저장소 ADR이다. 기존 Obsidian 사본은 저장소 기준으로 다시 썼다 | 두 벌이 서로 어긋나면 어느 쪽이 맞는지 알 수 없다. PR 리뷰를 거치는 쪽을 기준으로 둔다 |
| 읽는 순서의 입구는 Obsidian `00-Overview/Timeline.md` 하나로 둔다. 이슈 한 줄에 머지 시각, PR, Devlog, Rust 노트, ADR을 연결한다 | Devlog 날짜는 쓴 날이라 작업 순서와 맞지 않는다. 머지 순서가 코드가 쌓인 순서다 |
| 이슈 사이클 5단계에서 상세판 작성과 Timeline 한 줄 추가를 한다. 새 8단계는 사용자가 머지를 요청했을 때만 돌고, Devlog 수치와 Timeline 머지 시각을 PR 최종 상태로 맞춘다 | 이번 어긋남은 절차에 갱신 단계가 없어서 생겼다. 사람이 기억해야 하는 일을 절차로 옮긴다 |
| 규칙은 `docs/DEVELOPMENT.md` §8, `CLAUDE.md`, 스킬에 같은 내용으로 적는다. 형식은 스킬 폴더의 `obsidian-adr.md`에 둔다 | 스킬은 DEVELOPMENT.md와 CLAUDE.md가 우선한다고 정해 두었다. 우선하는 문서에 규칙이 없으면 스킬만 고쳐서는 적용되지 않는다 |
| 상세판을 쓰다 드러난 문서와 코드의 차이는 저장소 ADR 본문을 고치지 않고 `Follow-up (코드 대조)`로 붙인다. 빠진 구현은 #27로 분리한다 | 확정된 ADR 본문은 고치지 않는다는 규칙을 따른다. 구현은 테스트와 리뷰가 필요한 별도 작업이다 |

## 기각한 방안

- **Obsidian ADR 사본을 `_archive/`로 옮기고 저장소만 원본으로 두기.** 사용자가 두 곳 모두 관리하기로 했다. 대신 내용 깊이를 나눠 중복이 아니게 했다.
- **Rust 노트에 `issue`/`pr` 필드와 이전·다음 링크 달기.** Timeline이 같은 순서를 잡아 주므로 두 번 관리할 필요가 없어 하지 않았다.
- **Devlog를 실제 작업 날짜로 다시 나누기.** 커밋 시각을 보니 #7과 #10은 모두 11-08에 끝났고, 11-07에는 커밋이 없었다. 나눌 대상이 없었다.

## 손댈 때 주의

- 상세판의 이유가 출처(ADR, PR, 이슈, 코드, 대화)에 없으면 `(추론)`, 확인하지 못한 사실이면 `(미확인)`을 붙인다. #1 ADR들은 결정을 내린 대화가 남아 있지 않아 추론 표시가 많다.
- Obsidian 쪽은 PR 리뷰를 거치지 않는다. 저장 전에 `scan-sensitive.sh`를 통과해야 한다. 이 검사는 토큰 타입이 들어간 함수 시그니처나 환경변수 자리표시자도 비밀값으로 잡을 수 있다. 그럴 때는 해당 발췌를 글로 풀어 쓴다.
- 8단계는 사용자가 머지를 요청했을 때만 돈다. 사이클 자체는 계속 draft PR에서 멈춘다.

## Follow-up (2026-11-08, #29)

#27 사이클을 돌며 드러난 빈틈으로 이슈 사이클을 고쳤다.

| 결정 | 이유 |
|---|---|
| Obsidian 갱신(상세판, Devlog, Rust 노트, Timeline)을 새 7단계로 떼어 draft PR 생성 뒤에 한다. 머지 후 단계는 9단계가 된다 | 원래 5단계는 PR 링크를 적으라면서 PR보다 먼저 왔다. #27에서 순서를 바꿔 처리해야 했다 |

| 브랜치는 별도 worktree로, 구현과 리뷰 수정은 `pstack:poteto-agent`에, 메인은 설계·diff 검토·검증 재실행 | 사용자가 매번 요청하던 방식을 기본값으로 옮긴다. 마지막 리뷰의 몇 줄짜리 수정만 메인이 직접 할 수 있다 |

| jk 0.4.0 이상과 세션이 불러온 버전 일치를 0단계에서 확인한다. 리뷰 대상에 TypeScript를 넣는다 | 세션은 시작할 때의 플러그인 버전을 계속 써서, 업데이트 후에도 0.2.0으로 리뷰가 돌았다. #8부터 `web/` 작업이 주가 된다 |
